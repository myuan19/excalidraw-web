# 实验报告: 首页预览聚焦算法

## 问题描述

嵌入页面首页的 MindMap 预览图不再希望只做固定全局缩放或固定 root 占比裁剪，而是要先基于当前全局截图定位 root 与其他节点范围，再让预览中心更靠近 root，同时让不同节点数量下的 root 视觉大小保持温和变化。

## 问题原因

上一版 focused 策略仍然会让单节点与多节点之间的视觉尺寸差距偏大。特别是只有 root 或 root 后跟随非节点元素时，预览视野容易收得过紧，导致单节点看起来过大。之后又发现一个理解偏差：最终 `viewBox` 不应该被原始全局截图边界限制，否则 root 靠近边缘时无法居中。

## 解决方案

实验中把规则拆成四个可落地的计算步骤：

1. 以 SVG 的 `width` / `height` 作为当前全局截图范围，保留全局 SVG 作为原始对照。
2. 解析第一个 `.smm-node` 为 root，后续 `.smm-node` 合并成其他节点范围；图片目标中心取 `rootCenter + (otherCenter - rootCenter) * 0.2`。
3. 约 10 个节点时 root 视觉大小定义为 `1`；单节点约 `1.2`；节点很多时最低约 `0.8`。实验中基准 root 占视野宽度从 `28%` 缩小为当前的 `0.8`，即 `22.4%`，节点数量曲线控制最终 viewBox 大小。
4. `viewBox` 宽高保持由节点数量曲线决定；如果按 1/5 比例算出的目标中心会让 root 超出视窗中心 50% 区域，则只把中心点向 root 拉回到临界位置。最终 `viewBox` 允许超出原始全局截图边界，由卡片背景补足空白。

建议后续生产代码新增一个 MindMap viewBox 计算函数，放在 `app/data/thumbnailSvg.ts` 的 MindMap normalize 流程里，用该函数替换当前只回到全局 bounds 的 `cropMindMapViewBox()` 行为。

## 实验过程

1. 第一轮：创建 9 个压力样例，包括单 root、普通中等规模、很多同级节点、深链路、左侧展开、双侧展开、平衡树、垂直极端、远端节点簇。
2. 第一轮运行发现 `experiment.mjs` 清空整个 `output` 会删除 `run.sh` 正在写入的 `run.log`。
3. 第二轮：改为只清空 `output/svgs`，保留日志文件，重新运行后 `run.log`、`summary.json`、HTML 总览和 SVG 对照全部生成成功。
4. 第三轮：将缩放主控改为节点数量曲线，并新增“单节点 + 跟随元素”压力样例，验证单节点不会被过度放大。
5. 第四轮：移除 `viewBox` 对原始 SVG 边界的钳制，把限制改为“目标中心必须落在所有节点范围缩小 50% 后的安全区域内”，重新生成所有图片并删除旧图片输出。
6. 第五轮：将视觉比例 `1` 的绝对大小放大一倍，基准 root 占视野宽度从 `14%` 调整为 `28%`，相对比例 `1.2 -> 1 -> 0.8` 不变。
7. 第六轮：按反馈将第五轮的绝对大小缩小为当前 `0.8`，基准 root 占视野宽度从 `28%` 调整为 `22.4%`，相对比例仍不变。
8. 第七轮：把中心限制从“所有节点范围缩小 50% 的安全区”改为“root 必须落在视窗中心 50% 区域内”。尺寸不变，只在超出时把中心向 root 拉回。

## 关键结果

成功输出 10 组全局截图与新算法预览对照：

- 单 root：视觉比例约 `1.22`，接近目标 `1.2`。
- 单 root：`viewBox` 可越过原始边界，root 能处于预览中心。
- 单 root + 跟随元素：视觉比例约 `1.20`，不会再因为只有一个节点而收得过紧，也不会因为 root 靠近原始截图边界而偏离中心。
- 约 10 个节点：视觉比例约 `1.00`，作为基准。
- 多节点：视觉比例逐步降低，压力样例最低到 `0.80`。

这些结果符合“10 个节点左右为 1，单节点约 1.2，多节点最低约 0.8，差距不要过大”的实验目标。
